# Week6 회고

6주차에는 Apache Airflow를 활용하여 서울 공공자전거 API 데이터를 수집하고 정제한 뒤 대여소 단위로 집계하여 MySQL에 적재하는 ETL 파이프라인을 구축했습니다. API의 페이지네이션을 처리하고 여러 날짜의 데이터를 하나의 DAG에서 처리하면서 데이터 수집부터 변환, 적재까지의 전체 흐름을 직접 구현했습니다. 특히 동일한 작업을 다시 실행하거나 실패한 Task를 재실행하더라도 중복된 결과가 생성되지 않도록 멱등성을 고려하며, 실제 데이터 파이프라인에서는 정상적인 실행뿐만 아니라 Retry와 Backfill까지 고려해야 한다는 점을 학습했습니다.

메인 프로젝트의 주제를 구체화하는 과정도 계속 진행했습니다. NYC TLC와 서울 공공자전거 데이터를 기반으로 여러 아이디어를 검토하면서 단순히 흥미로운 분석 주제를 만드는 것보다 실제 운영자가 겪는 문제인지, 필요한 데이터를 확보할 수 있는지, 그리고 지속적으로 데이터를 수집하고 처리할 이유가 있는지를 중심으로 프로젝트를 바라보려고 했습니다. 이 과정에서 데이터의 제공 주기와 활용 시점을 고려하여 수집, 정제, 집계 작업의 주기를 설계하고 Bronze, Silver, Gold 계층에서 각각 어떤 데이터를 관리해야 하는지도 고민했습니다.

또한 프로젝트 아키텍처를 설계하면서 Airflow, Lambda, S3, EMR, RDS, EC2 등의 역할을 정리하고 각 기술을 어느 단계에서 사용하는 것이 적절한지 학습했습니다. 특히 Airflow에서 Lambda 작업이 실패했을 때 Retry와 재실행이 어떻게 이루어지는지, 과거 데이터를 Backfill하기 위해 처리 대상 날짜를 어떻게 전달해야 하는지 등을 살펴보며 장애와 재처리를 고려한 파이프라인 설계의 중요성을 이해했습니다. Terraform과 같은 IaC 도구에 대해서도 알아보면서 클라우드 인프라를 반복 가능하게 관리하는 방법을 학습했습니다.

다만 프로젝트에 활용할 수 있는 기술이 많아지면서 아키텍처에 기술을 추가하는 것 자체에 집중할 위험이 있다는 점을 느꼈습니다. Lambda, EMR, RDS와 같은 기술을 사용하는 것보다 각각이 어떤 문제를 해결하는지 설명할 수 있어야 했고, 데이터의 업데이트 주기와 실제 활용 방식이 맞지 않으면 복잡한 파이프라인을 구축하더라도 의미가 없다는 점도 알게 되었습니다. 또한 실제 API를 이용한 ETL 과정에서는 호출량 제한과 같은 외부 시스템의 제약으로 인해 예상하지 못한 실패가 발생할 수 있다는 점을 경험했습니다.

다음 주차에는 프로젝트의 문제 정의와 데이터 흐름을 먼저 확정한 뒤 필요한 기술을 선택하는 방식으로 아키텍처를 구체화하겠습니다. 또한 정상적인 데이터 처리 과정뿐만 아니라 API 장애, 중복 수집, Task 실패와 같은 상황에서도 안정적으로 복구할 수 있도록 Retry, Backfill, 멱등성, 데이터 품질 검증을 함께 고려하겠습니다. 이를 통해 단순히 여러 기술을 사용하는 프로젝트가 아니라 각 기술의 사용 이유와 데이터 흐름을 명확하게 설명할 수 있는 데이터 파이프라인을 만드는 것을 목표로 하겠습니다.
