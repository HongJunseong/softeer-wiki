# Week8 회고

8주차에는 Adaptive Query Execution이 런타임 통계를 이용해 Spark SQL의 Physical Plan을 보완하는 방식을 학습했습니다. Query Stage와 Exchange의 관계를 살펴보고 Initial Plan과 Final Plan을 비교하면서, 실행 전에 알 수 없었던 실제 데이터 크기와 분포가 후속 연산 선택에 어떻게 반영되는지 확인했습니다. 이를 통해 Catalyst의 정적 최적화와 AQE의 동적 최적화가 서로 대체하는 기능이 아니라 연속된 과정이라는 점을 이해했습니다.

세부 기능으로는 Shuffle 이후의 작은 파티션을 합치는 기능, 데이터 편향이 큰 파티션을 나누는 Skew Join 최적화, 런타임 크기에 따라 Sort Merge Join을 Broadcast Hash Join으로 바꾸는 기능을 다뤘습니다. 파티션 병합에서는 Task 수와 파일 크기의 균형을, Skew 처리에서는 최장 Task와 키 분포를, 조인 전환에서는 각 Stage의 실제 바이트 크기를 확인해야 한다는 판단 기준을 세웠습니다. Local Shuffle Reader가 네트워크 이동을 줄이는 조건도 실행 계획에서 함께 살펴보았습니다.

AQE를 켜는 것만으로 모든 작업이 빨라지는 것은 아니었습니다. 임계값을 데이터 특성과 맞지 않게 설정하면 불필요한 분할이나 병합이 생길 수 있고, 처리 시간이 짧은 쿼리에서는 적응형 최적화의 효과가 작을 수도 있었습니다. 평균 실행 시간만 보면 일부 Task에 집중된 병목을 놓칠 수 있어 Spark UI의 분포와 Shuffle 지표를 함께 확인하는 습관이 필요했습니다.

다음 주에는 이번에 만든 성능 판단 기준을 메인 프로젝트에 적용하겠습니다. 원천 데이터의 특성과 예상 조회 패턴을 먼저 확인하고, 파티션 구조와 조인 방식을 설계한 뒤 실제 지표를 이용해 선택이 적절했는지 검증하겠습니다.
