# Week7 회고

7주차에는 Spark SQL의 Catalyst Optimizer가 사용자의 쿼리를 실행 가능한 계획으로 변환하는 전 과정을 학습했습니다. Unresolved Logical Plan이 Analyzer를 거쳐 해석되고, 여러 최적화 규칙이 적용된 뒤 물리 연산자로 선택되는 흐름을 정리하면서 `explain()` 결과를 단계별로 읽는 기준을 만들었습니다. 이전에는 실행 계획을 단순히 긴 출력으로 보았다면, 이번 주에는 각 계획이 어떤 책임을 가지며 다음 단계로 무엇을 전달하는지 중심으로 살펴볼 수 있었습니다.

Rule-Based Optimization에서는 상수 계산과 불리언 식 단순화 같은 규칙뿐 아니라 Column Pruning, Predicate Pushdown, Partition Pruning이 실제 읽기 범위를 줄이는 과정까지 확인했습니다. 특히 필터를 작성하는 것과 데이터 소스 수준에서 필터가 적용되는 것은 다르다는 사실을 알게 되었고, 저장 형식과 파티션 설계가 쿼리 성능에 직접 연결된다는 점을 이해했습니다. 조인 실습에서는 테이블 통계와 데이터 크기에 따라 Broadcast Hash Join과 Sort Merge Join 등의 전략이 달라지는 것도 비교했습니다.

가장 큰 어려움은 특정 최적화 기법의 이름을 아는 것과 실제 계획에서 적용 여부를 판단하는 일이 다르다는 점이었습니다. 통계가 부정확하면 예상한 조인 전략이 선택되지 않았고, UDF처럼 Catalyst가 내부를 해석하기 어려운 표현은 최적화 범위를 제한했습니다. 또한 한 번의 실행 시간만으로 성능을 판단하면 캐시와 실행 환경의 영향을 구분하기 어렵다는 점도 확인했습니다.

다음 주에는 정적인 계획만 분석하는 데서 나아가 실행 중 수집되는 통계가 계획을 어떻게 바꾸는지 학습하겠습니다. 동일한 쿼리에 대해 초기 계획과 최종 계획, Task 및 Shuffle 지표를 함께 비교하여 Spark의 최적화를 실제 실행 결과와 연결하는 연습을 이어가겠습니다.
